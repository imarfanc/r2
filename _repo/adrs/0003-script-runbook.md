# ADR 0003: A script runbook on the Deno shape

- **Status:** accepted
- **Date:** 2026-08-07

## Context

The application this repository now serves is a runbook: a browser view over a directory of local scripts, with one page per group, a run button, and terminal output streamed back as it happens. It was previously a Bun and React application that bundled two pages with `bun build`, highlighted source with Shiki, and ran scripts through `Bun.spawn`.

Moving it onto this repository's Deno shape meant deciding what to keep. The scripts themselves are the valuable part and are worth nothing if they have to be rewritten.

## Decision

**The scripts move across untouched.** `data/scripts/` holds them exactly as they were, and the runner picks a launcher per script — `bash`, `zsh`, `uv run`, `bun run`, `osascript`, `swift`. Those runtimes belong to the machine running the server, in the same way `cursor` does; the repository stays Deno-only, which is a statement about the repository's own toolchain, not about what a script may be written in. `data/` is therefore excluded from `deno fmt`, `deno lint`, and the structural content checks: formatting someone else's Python to Deno's taste would be the wrong kind of tidy.

**The frontends drop React and the build step.** Both versions are plain ES modules served straight from `public/frontends/`, which is what makes `deno task dev` the whole development loop. The cost is Shiki: a highlighter that ships grammars cannot survive without a bundler, so `shared/highlight.js` replaces it with a shallow regex pass over comments, strings, numbers and keywords. The source view exists to read a script at a glance, not to edit it, and that is the level of fidelity it needs.

**Behaviour lives in `shared/`, drawing lives in the version.** `shared/catalog.js` owns loading a group, the selection, running, and remembering the result; a version folder holds only its own rendering. Adding `v3` is then a design exercise rather than a second implementation of the same state machine, which is what `FRONTENDS` was for in ADR 0002.

**Both versions share the layout and differ in voice.** `v2` began as a different arrangement — the group collapsed into a strip of chips above a full-width console — and it read as a different application rather than a second design of the same one. It now uses `v1`'s rail and console, and carries its own typography, palette and density instead: warm serif and amber against cool mono and cyan. A version is a restyling with room for a feature of its own, which is how `v2` keeps its filter over the index.

**Every version carries every group.** URLs are `/<version>/<group>/`, `/` redirects to the default pair, and a bare `/<version>/` opens the default group. The version and group lists reach the browser through `/shared/config.js`, generated by `src/app/client-config.ts` from `src/config.ts` — a hand-written copy under `public/` would drift the first time someone added a page.

## Consequences

- Adding a script is making a directory with a `script.yaml`; there is no registration step and no restart.
- Adding a group means `SCRIPT_GROUPS` plus one page folder per frontend version, and the checks will not catch a missing one — the handler test does.
- A run holds a response open for as long as the script runs. The stream carries a zero-width heartbeat so a quiet script is not mistaken for a dead connection, and shutdown stops the children before the server.
- Losing Shiki means unusual languages fall back to plain text rather than to a wrong grammar.
